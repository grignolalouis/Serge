\section{Summary}
% =====================================================================

This week focused on two goals: \textbf{stabilising the codebase} and making SERGE \textbf{easy to use for anyone}. We went through the entire Go backend to catch edge cases and tighten the data model, and we reworked the MCP integration so that SERGE can be plugged into any desktop agent client in a few clicks.

% =====================================================================
\section{Code Hardening \& Data Model Refinement}
% =====================================================================

\subsection{What We Did}

After the first round of agent testing (Week~8), we noticed a few areas where the code and data were fragile. This week we went through the full stack --- domain models, repositories, services, controllers, and seed data --- to fix issues and improve robustness.

\subsection{Data Model Fixes}

\begin{table}[H]
\centering\small
\caption{Data model issues identified and resolved.}
\begin{tabularx}{\textwidth}{@{} L{4cm} X @{}}
\toprule
\thead{Issue} & \thead{Resolution} \\
\midrule
Inconsistent stock movement references & Standardised \texttt{reference\_type} values to \texttt{supplier\_order} and \texttt{customer\_order} across all data files and the seed generator. \\
Missing supplier product links & Verified every \texttt{SupplierOrderLine.supplier\_product\_id} points to a valid \texttt{SupplierProduct}, and every \texttt{SupplierProduct.product\_id} maps to an existing \texttt{Product}. \\
Scenario data integrity & Ran a verification script against all 15 evaluation scenarios to confirm ground truth values match the actual seed data (ORD-007 status, PROD-001 inventory, PO-008 details, SHP-009 exception). \\
Seed generator idempotency & The seed generator (\texttt{cmd/seedgen}) now produces identical output on every run (fixed random seed = 42), making results fully reproducible. \\
\bottomrule
\end{tabularx}
\end{table}

\subsection{Code Quality Improvements}

\begin{itemize}[itemsep=0.5em]
    \item \textbf{Seed loader refactored} using Go generics --- one \texttt{loadEntities[T]} function replaces 12 repetitive load blocks, reducing the loader from 90 lines to 40.
    \item \textbf{Repository loaders} simplified to one-liner methods for consistency.
    \item \textbf{Main server startup} condensed --- repository, service, and controller creation now fits in a single readable block.
    \item \textbf{Dead code removed} --- old \texttt{GetShipmentByOrder} (single return) replaced by \texttt{ListShipmentsByCustomerOrder} (supports split shipments).
\end{itemize}

\begin{keyinsight}
These changes are not visible to the end user, but they matter for the project's credibility. A clean, well-tested codebase shows that we understand software engineering beyond just ``making it work.'' The seed generator's reproducibility is particularly important for evaluation: anyone can regenerate the exact same 500-order dataset and verify our results.
\end{keyinsight}

\section{MCP Integration \& Desktop UI}
% =====================================================================

\subsection{The Problem}

Until now, using SERGE required command-line knowledge: building the Go binary, configuring \texttt{.mcp.json}, and running Claude Code in a terminal. This is fine for developers but not for the operations managers who are our target users.

\subsection{How MCP Makes This Easy}

The Model Context Protocol was designed to be a universal plug --- like USB-C for AI agents. Our MCP server communicates over \textbf{stdio} (standard input/output), which means any MCP-compatible client can launch it as a subprocess and immediately access all 35 supply chain tools.

\subsection{Desktop Integration}

SERGE is now pluggable into any MCP-compatible desktop agent in a few steps:

\begin{enumerate}[itemsep=0.5em]
    \item \textbf{Build the binary:} one command (\texttt{go build -o serge-mcp cmd/server/main.go}).
    \item \textbf{Add to your agent client:} point the client to the binary and the data folder. For Claude Desktop, this means adding a few lines to the MCP configuration file. For other clients (Cursor, Windsurf, or any MCP-compatible tool), the process is similar.
    \item \textbf{Start using it:} the agent immediately sees all 35 tools and can answer supply chain questions.
\end{enumerate}

\begin{table}[H]
\centering\small
\caption{SERGE integration with different agent clients.}
\begin{tabularx}{\textwidth}{@{} l l X @{}}
\toprule
\thead{Client} & \thead{Setup} & \thead{Notes} \\
\midrule
Claude Code (CLI)    & \texttt{.mcp.json} in project folder & Already working since Week~8 \\
Claude Desktop (Mac) & Add to MCP settings & Full GUI, no terminal needed \\
Cursor / Windsurf    & MCP server config & IDE-integrated agent \\
Custom agent         & Connect via stdio & Any MCP SDK (Python, TS, Go) \\
\bottomrule
\end{tabularx}
\end{table}

\begin{keyinsight}
This is a key result of the project: SERGE is \textbf{agent-agnostic}. We built the supply chain infrastructure once, and any AI agent can plug into it. Switching from Claude to GPT or Llama requires zero changes to our code --- only the agent client changes. This validates our architecture choice of using MCP as the integration layer.
\end{keyinsight}

\subsection{What the User Sees}

From the user's perspective, the experience is simple: open their desktop agent (e.g., Claude Desktop), and ask questions in natural language. The agent calls SERGE's MCP tools in the background and returns a structured answer. The user never interacts with the supply chain systems directly.

Example interaction:

\begin{quote}
\textbf{User:} ``Why is order ORD-007 stuck?''

\textbf{Agent:} Checks OMS (order stuck in processing, needs 50 units of Nam Doc Mai), checks TMS (no shipment created), checks WMS (only 8 units in stock), checks SRM (PO-008 incoming with 150 units, arriving Feb 18). Returns a full diagnostic with root cause and timeline.

\textbf{Time:} $<$60 seconds vs. 15--30 minutes manually.
\end{quote}
